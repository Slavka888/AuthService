# AuthService

**AuthService** — сервис регистрации и аутентификации пользователей на **Go** с **gRPC API**, хранением данных в **SQLite** и выдачей **JWT-токенов**. Проект разделяет транспортный слой, бизнес-логику и работу с базой данных, а также включает SQL-миграции и интеграционные тесты.

## Возможности

- **Регистрация** пользователя по email и паролю.
- **Авторизация** с проверкой пароля и выдачей JWT для выбранного приложения.
- **Проверка роли администратора** по идентификатору пользователя.
- **Безопасное хранение паролей**: вместо открытого пароля в базе сохраняется хеш `bcrypt`.
- **Настройка через YAML**: режим окружения, путь к БД, время жизни токена и порт gRPC.
- **SQL-миграции** для создания таблиц и начальных данных.
- **Graceful shutdown** при получении `SIGINT` или `SIGTERM`.

## Быстрый старт

### Требования

- **Go 1.27.3** (версия, заданная проектом).
- **Docker** с поддержкой `docker compose` — для запуска SQL-миграций.
- **Make** — для команд из `makefile`.
- По желанию: **grpcurl** для проверки gRPC API из терминала.

> В архиве есть два Go-модуля. Не перемещайте `auth-service/` отдельно от `protos/`: их связывает `go.work` в корне проекта.

### 1. Перейдите в директорию сервиса

После распаковки архива:

```bash
cd AuthService/auth-service
```

### 2. Примените миграции

```bash
make migrate-up
```

Команда запускает через Docker Compose инструмент `golang-migrate`, который применяет SQL-файлы из `migrations/` к `storage/auth.db`. Миграции создают таблицы `users` и `apps`, добавляют поле `is_admin` и тестовую запись приложения с `id = 1`.

> `docker compose` в этом проекте предназначен **для миграций**, а не для запуска самого gRPC-сервера. В архиве уже присутствует файл `storage/auth.db`; если схема в нём актуальна, новых миграций может не быть.

### 3. Запустите сервис

```bash
make auth-service-run
```

Альтернативный способ:

```bash
go run ./cmd/auth-service/main.go
```

По умолчанию используется `config/local.yaml`, а gRPC-сервер слушает порт **44044**. Остановить сервер можно сочетанием `Ctrl+C`.

Для явного указания конфигурации:

```bash
go run ./cmd/auth-service/main.go -config ./config/local.yaml
```

## gRPC API

Контракт находится в `protos/proto/auth-service/auth.proto`. Реализовано три RPC-метода:

| Метод | Параметры | Результат |
| --- | --- | --- |
| `auth_service.Auth/Register` | `email`, `password` | `user_id` созданного пользователя |
| `auth_service.Auth/Login` | `email`, `password`, `app_id` | Подписанный JWT в поле `token` |
| `auth_service.Auth/IsAdmin` | `user_id` | Логическое значение `is_admin` |

### Примеры запросов

Запускайте следующие команды **из каталога `auth-service/`**, пока сервер работает в другом терминале. Для `grpcurl` указан исходный `.proto`-файл, поскольку в текущей реализации не включён gRPC Server Reflection.

**Регистрация пользователя:**

```bash
grpcurl -plaintext \
  -import-path ../protos/proto \
  -proto auth-service/auth.proto \
  -d '{"email":"user@example.com","password":"my_password_123"}' \
  localhost:44044 auth_service.Auth/Register
```

**Вход и получение JWT:**

```bash
grpcurl -plaintext \
  -import-path ../protos/proto \
  -proto auth-service/auth.proto \
  -d '{"email":"user@example.com","password":"my_password_123","app_id":1}' \
  localhost:44044 auth_service.Auth/Login
```

**Проверка прав администратора:**

```bash
grpcurl -plaintext \
  -import-path ../protos/proto \
  -proto auth-service/auth.proto \
  -d '{"user_id":1}' \
  localhost:44044 auth_service.Auth/IsAdmin
```

Замените `user_id` на идентификатор, полученный при регистрации. Пользователи создаются с `is_admin = false` по умолчанию.

### Что содержится в JWT

После успешного входа сервис выдаёт токен с подписью **HS256**. В полезной нагрузке присутствуют:

- `user_id` — идентификатор пользователя;
- `email` — email пользователя;
- `app_id` — идентификатор приложения;
- `exp` — время окончания действия токена.

Срок действия задаётся параметром `token_ttl`. Для подписи используется `secret` соответствующего приложения из таблицы `apps`.

## Конфигурация

Основной файл: `auth-service/config/local.yaml`.

```yaml
env: "local"
storage_path: "./storage/auth.db"
token_ttl: 1h
grpc:
  port: 44044
  timeout: 10h
```

| Параметр | Описание |
| --- | --- |
| `env` | Режим логирования: `local`, `dev` или `prod` |
| `storage_path` | Путь к файлу SQLite относительно рабочей директории |
| `token_ttl` | Срок действия JWT |
| `grpc.port` | Порт gRPC-сервера |
| `grpc.timeout` | Параметр конфигурации, используемый тестовым клиентом для тайм-аута контекста |

Для `local` логи выводятся текстом на уровне `debug`, для `dev` — в формате JSON на уровне `debug`, для `prod` — в формате JSON на уровне `info`.

## Работа с миграциями

Команды запускаются из `auth-service/`:

```bash
make migrate-up      # применить миграции
make migrate-down    # откатить миграции
make migrate-create seq=название_миграции
```

> **Осторожно:** `make migrate-down` может удалить данные при откате SQL-миграций. Используйте его на тестовой базе или после резервного копирования.

Существующие миграции:

1. `000001_init` — таблицы `users` и `apps`.
2. `000002_add_is_admin_column_to_user` — поле `is_admin`.
3. `000003_added_app` — демонстрационное приложение с `id = 1`.

## Тестирование

В `auth-service/tests/` находятся интеграционные тесты регистрации, входа и обработки повторной регистрации. Они обращаются к **уже запущенному** gRPC-серверу на `localhost:44044` и используют `config/local_test.yaml`.

В одном терминале запустите сервер:

```bash
make auth-service-run
```

Во втором, находясь в `auth-service/`, выполните:

```bash
go test ./tests/... -v
```

**Особенность текущих тестов:** проверки повторной регистрации и входа ожидают, что пользователь `33_test@example.com` с паролем `testpassword` уже существует в тестовой БД. Без этих данных тесты могут завершиться ошибкой. Тест `TestLoginWithExpiredToken`, несмотря на название, не проверяет фактическую работу сервиса с истёкшим токеном.

## Архитектура

```text
gRPC-клиент
     │
     ▼
gRPC handlers (валидация и ответы)
     │
     ▼
Auth service (бизнес-логика)
     ├── bcrypt → проверка/хеширование пароля
     ├── JWT    → генерация токена
     │
     ▼
SQLite storage (users, apps)
```

Обработчики gRPC не работают с SQL напрямую. Бизнес-логика получает зависимости через интерфейсы `UserSaver`, `UserProvider` и `AppProvider`, что позволяет отделить её от реализации хранилища.

## Ограничения и дальнейшее развитие

**Для применения в production следует внести ряд доработок.** В частности:

- В миграции создаётся приложение с демонстрационным секретом — для реального развёртывания необходимы отдельные защищённые секреты.
- gRPC-сервер запускается без TLS; в примерах применяется `-plaintext` только для локального тестирования.
- Метод `IsAdmin` принимает `user_id`; проверка полномочий самого вызывающего клиента пока не реализована.
- Ошибки из бизнес-логики сейчас преимущественно преобразуются в общий gRPC-код `Internal` — полезно добавить точные коды ошибок.
- Интеграционные тесты стоит изолировать от постоянной базы и создавать тестовые данные автоматически.
- Docker Compose пока содержит только инструмент миграций, а не полноценный контейнер сервиса.
